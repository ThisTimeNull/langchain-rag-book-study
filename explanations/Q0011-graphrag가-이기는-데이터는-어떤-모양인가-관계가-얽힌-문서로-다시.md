# Q0011 · GraphRAG가 이기는 데이터는 어떤 모양인가? (관계가 얽힌 문서로 다시 붙여보기)

- **태그**: graphrag
- **날짜**: 2026-09-06
- **코드**: [`code/Q0011_graphrag_wins.py`](../code/Q0011_graphrag_wins.py)

## ❓ 질문
[[Q0010-graphrag는-vectorrag와-무엇이-다른가-llm으로-문서에서-]]에서 GraphRAG가 졌다.
문서가 평평한 규칙 나열이라 불리했다. 관계가 얽힌 데이터로 바꾸면 판이 뒤집힐까?

## 💡 한 줄 답
> 뒤집힌다. 단, 조건이 두 개다.
> **하나, 벡터가 조각 몇 개로 못 모으는 긴 사슬 질문이어야 한다.**
> **둘, 그래프가 정확해야 한다. LLM 추출로 만든 그래프는 부정확해서 오히려 졌다.**

## 📖 설명

### 데이터를 다시 만들었다

팀 8개, 사람 32명, 서비스 20개, 의존 관계 24개를 `data/graph_sample/`에 만들었다.
핵심은 **답이 한 문단에 없다**는 것이다.

```
"결제 API가 의존하는 서비스를 운영하는 팀의 온콜 담당자는?"

  결제 API ─의존→ 인증 서비스 ─운영─ 인프라팀 ─온콜→ 김철수
  (service_deps.md)      (service_owner.md)  (oncall.md)
```
사실 세 개가 문서 세 개에 흩어져 있다.

### 세 번의 실험 결과

같은 질문 5개를 세 가지 조건으로 돌렸다.

| 질문 | 난이도 | Vector | Graph (LLM 추출) | Graph (규칙 적재) |
|---|---|:---:|:---:|:---:|
| 인프라팀 팀장은? | 1다리 | ✅ | ✅ | ✅ |
| 결제 API가 의존하는 서비스의 운영팀은? | 2다리 | ✅ | ❌ 결제팀 | ✅ |
| 그 팀의 온콜 담당자는? | 3다리 | ✅ | ❌ 모름 | ✅ |
| 추천 엔진이 의존하는 서비스 전부 | 짧은 사슬 | ✅ | ❌ 모름 | ✅ |
| **감사 로그가 의존하는 서비스 개수** | **17다리** | ❌ **4개** | ❌ 20개 | ✅ **17개** |

**규칙으로 적재한 그래프만 5문제를 다 맞혔다.** LLM으로 추출한 그래프는 1개만 맞혔다.

### ⭐ 발견 1 - 벡터는 긴 사슬에서 무너진다

5번 질문이 유일하게 벡터가 확실히 진 문제다. 정답 17개를 **4개**라고 답했다.

이유는 단순하다. 17다리를 세려면 의존 관계 17줄이 **전부** 필요하다.
벡터는 질문과 비슷한 조각 k개만 가져온다. k를 아무리 키워도 사슬 전체를 담보하지 못한다.
그래프는 한 줄이면 끝난다.

```cypher
MATCH (l:서비스 {id:'감사 로그'})-[:의존*1..]->(s:서비스) RETURN count(DISTINCT s)
```

**이게 GraphRAG를 쓰는 이유의 전부다.** 반대로 1~4번처럼 2, 3다리짜리는 벡터도 잘 풀었다.
질문에 "결제 API", "의존", "운영", "온콜"이 다 들어 있어서, 유사도 검색만으로 필요한 조각이
그대로 딸려왔기 때문이다.

> 교훈: **다중 홉이라고 다 GraphRAG가 필요한 게 아니다.** 중간 대상을 질문에서 이름으로
> 부를 수 있으면 벡터도 푼다. 사슬이 길어서 조각으로 못 모을 때 비로소 갈린다.

### ⭐ 발견 2 - LLM 추출이 그래프의 천장을 정한다

LLM이 만든 그래프를 원문과 대조했다.

```
원문 의존 관계 24개  →  그래프에 들어온 것 16개  (33% 누락)

누락된 것:
  감사 로그 -> 환율 서비스
  환율 서비스 -> 메시지 큐
  메시지 큐 -> 재고 관리
  ...
```

**사슬이 한 군데만 끊겨도 다중 홉 질문은 무너진다.** 5번 질문에서 `감사 로그`는
나가는 간선이 아예 없어서 결과가 0건이었다.

청크를 400자에서 150자로 줄여 다시 추출했다. 누락 개수는 8개로 같았지만
**빠진 간선이 달라졌다.** 그 결과 2, 3, 4번이 새로 틀렸다.
[[Q0010-graphrag는-vectorrag와-무엇이-다른가-llm으로-문서에서-]]에서 본 비결정성이 또 나왔다.

### ⭐ 발견 3 - 엔티티 이름이 안 맞으면 다 소용없다

처음에 그래프가 2, 3번을 못 푼 진짜 이유는 따로 있었다.

```
원문:   결제 API,  사용자 DB
그래프: 결제 Api,  사용자 Db      ← LLM이 제목처럼 바꿔 뽑았다
```

LLM이 짠 Cypher는 `{id:'결제 API'}`로 찾는데, 노드는 `결제 Api`다. 0건이 나온다.
관계는 전부 제대로 뽑혔는데 **이름 하나 때문에** 질의가 통째로 실패했다.

코드에 `align_ids_to_source()`를 넣어 원문 표기로 되돌렸더니 2번이 바로 풀렸다.
이게 GraphRAG에서 말하는 **엔티티 정합(entity resolution)** 문제다. 실무에서는 별칭 사전이나
임베딩 유사도로 더 정교하게 푼다.

### ⭐ 발견 4 - 정형 데이터에 LLM 추출을 쓰지 마라

가장 중요한 깨달음이다. 우리 문서는 이렇게 생겼다.

```markdown
- 결제 API는 인증 서비스에 의존한다.
- 인프라팀이 인증 서비스를 운영한다.
```

**문장 틀이 정해져 있다. 이미 정형 데이터다.** 정규식 다섯 줄이면 100% 정확하게 읽는다.

```python
rules = [
    (r"- (.+?)는 (.+?)에 의존한다\.", "서비스", "서비스", "의존"),
    ...
]
```

`--direct` 모드가 이 방식이다. 누락이 없고, 매번 같은 결과가 나오고, LLM 비용이 0이다.
그리고 5문제를 다 맞혔다.

> **LLM 추출은 문장 틀이 없는 비정형 문서에나 필요하다.** 회의록, 뉴스, 계약서처럼
> 사람이 자유롭게 쓴 글이 그렇다. 이미 구조가 있는 데이터를 LLM에 통과시키면
> 정확도를 잃기만 한다. GraphRAG를 검토할 때 제일 먼저 물어야 할 질문이다.
> "이 데이터, 정말 LLM이 읽어야 하나?"

## 🔗 코드와 연결

```bash
.venv/bin/python code/Q0011_graphrag_wins.py --rebuild   # LLM으로 추출
.venv/bin/python code/Q0011_graphrag_wins.py --direct    # 규칙으로 적재
.venv/bin/python code/Q0011_graphrag_wins.py             # 기존 그래프 재사용
```

두 모드를 번갈아 돌리면 같은 질문의 답이 어떻게 갈리는지 바로 보인다.

**공정한 비교를 위한 장치**: 코드가 실행할 때 벡터가 코퍼스의 몇 퍼센트를 보는지 출력한다.
처음 실험에서는 조각이 3개뿐인데 k를 4로 잡아서, 벡터가 **전체 문서를 통째로** LLM에 넣고 있었다.
그건 다중 홉을 푼 게 아니라 그냥 다 읽은 것이다. 코퍼스가 작으면 비교 자체가 성립하지 않는다.
