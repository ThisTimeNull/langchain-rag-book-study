# Q0017 · 규칙과 LLM을 섞어 추출하면? (규칙으로 긁고 남은 것만 LLM에 넘기기)

- **태그**: graphrag
- **날짜**: 2026-09-13
- **코드**: [`code/Q0017_hybrid_extraction.py`](../code/Q0017_hybrid_extraction.py)

## ❓ 질문
Q0011에서 정형 문서는 규칙이, Q0012에서 산문은 LLM이 이겼다. 실무 문서는 둘이 섞여 있다.
그러면 둘을 섞어 쓰면 되지 않나?

## 💡 한 줄 답
> 된다. 그런데 **"섞는다"는 말에 함정이 있다.** 같은 사실이 양쪽에서 나오면 충돌한다.
> 규칙이 `(인프라팀)-[운영]->(인증 서비스)`를 만들고 LLM이 `(인증 서비스)-[운영]->(인프라팀)`을
> 또 만든다. **누구를 믿을지 정해두지 않으면 하이브리드가 LLM만 쓸 때보다 나빠진다.**

## 📖 설명

### 실험 설계

코퍼스를 섞었다.

```
data/mixed_sample/
  roster.md            정형 목록 9줄   "- 정하늘은 인프라팀의 팀장이다."
  weekly_meeting.md    회의록          Q0012의 산문 3개
  incident_review.md   장애 회고
  handover.md          인수인계 메모
```

정답 11개 중 7개는 정형 목록에 있고, 의존 관계 4개는 산문에만 있다.
그리고 일부 사실은 **양쪽에 다 있다.** "인프라팀이 인증 서비스를 운영한다"는 목록에도 있고,
회의록에 "인증 서비스는 인프라팀 소관이라"로도 있다.

하이브리드는 이렇게 한다.

1. 조각마다 규칙을 먼저 돌린다
2. 규칙이 하나라도 읽은 조각은 규칙 결과만 쓴다
3. 규칙이 못 읽은 조각만 LLM에 보낸다
4. 합친다. 겹치면 규칙을 믿는다

### 결과

| 방식 | 정답 | 정답 외 | 방향 오류 | LLM 호출 |
|---|:---:|:---:|:---:|:---:|
| 규칙만 | 7/11 | 1 | 0 | 0 |
| LLM만 | 11/11 | 10 | 1 | 7 |
| 하이브리드 (충돌 해소 없이) | 11/11 | 15 | **2** | 6 |
| 하이브리드 (충돌 해소 후) | 11/11 | 11 | **0** | 6 |

"방향 오류"는 `(인증 서비스)-[운영]->(인프라팀)`처럼 거꾸로 뽑힌 관계의 개수다.

### ⭐ 발견 1: 처음 만든 하이브리드는 LLM만 쓸 때보다 나빴다

방향 오류가 LLM만일 때 1개, 하이브리드에서 2개였다. 섞었는데 더 틀렸다.

이유는 이렇다. 규칙이 목록에서 `(인프라팀)-[운영]->(인증 서비스)`를 정확히 만들었다.
그런데 회의록 조각에는 규칙이 읽을 문장 틀이 없으니 그 조각은 LLM에 갔고,
LLM은 "인증 서비스는 인프라팀 소관"을 거꾸로 읽어 `(인증 서비스)-[운영]->(인프라팀)`을 만들었다.
**둘 다 그래프에 남았다.** 맞는 것과 틀린 것이 나란히.

설계에는 "겹치면 규칙을 믿는다"고 써뒀는데 구현을 안 했다. 그러니 섞은 만큼 오류도 섞였다.

### ⭐ 발견 2: 충돌 해소를 넣으니 방향 오류가 0이 됐다

규칙이 만든 관계에는 `source='rule'`을 찍어둔다. LLM이 만든 관계에는 없다.
그러면 이렇게 정리할 수 있다.

```cypher
MATCH (a)-[r]->(b) WHERE r.source = 'rule'
MATCH (b)-[x]->(a) WHERE type(x) = type(r) AND x.source IS NULL
DELETE x
```

"규칙이 a→b라고 했는데 LLM이 b→a라고 한 게 있으면 LLM 것을 지운다."
두 개가 지워졌고 방향 오류가 0이 됐다.

**규칙이 읽은 사실은 방향이 틀릴 수 없다.** `- (.+?)이 (.+?)를 운영한다`라는 패턴에
방향이 박혀 있으니까. 그래서 규칙을 우선하는 게 맞다. 이게 Q0016에서 못 풀었던
방향 문제의 답이다. LLM에게 방향을 가르치는 게 아니라 **방향이 확실한 출처를 우선**한다.

### ⭐ 발견 3: 이름 정합도 "바꾸기"가 아니라 "합치기"여야 했다

첫 실행은 유일성 제약 위반으로 죽었다.

```
규칙이 만든 노드:  결제 API
LLM이 만든 노드:   결제 Api
```

Q0011부터 써온 이름 정합은 `결제 Api`의 id를 `결제 API`로 **바꾸는** 것이었다.
그런데 `결제 API`가 이미 있으니 같은 id가 둘이 된다. Neo4j가 막는다.

바꾸는 게 아니라 **합쳐야** 한다. 중복 노드에 붙은 관계를 정식 노드로 옮기고 중복을 지운다.

```cypher
MATCH (canon:__Entity__ {id:'결제 API'}), (dup:__Entity__ {id:'결제 Api'})
CALL apoc.refactor.mergeNodes([canon, dup], {properties:'discard', mergeRels:true})
```

한 출처만 쓸 때는 안 드러났던 문제다. 두 출처를 섞으니 같은 것이 두 번 만들어졌고,
그제서야 "정합"이 이름 바꾸기가 아니라 노드 병합이라는 게 분명해졌다.

### ⭐ 발견 4: 호출 절감은 정형 비중에 비례한다

LLM 호출이 7에서 6으로 줄었다. 하나다. 정형 목록이 조각 하나뿐이라서 그렇다.
정형 문서가 절반이면 호출도 절반으로 준다. 이 실험 규모로는 절감 효과를 말하기 어렵다.

### ⭐ 발견 5: LLM만이 11/11인 건 운이다

같은 산문에 대해 Q0012에서 9/11, Q0016에서 9와 11이 나왔다. 이번엔 11이다.
LLM 추출은 실행마다 다르다. "LLM만으로도 다 맞혔으니 하이브리드가 필요 없다"고
읽으면 안 된다. 하이브리드의 값은 재현율이 아니라 **정형 부분이 흔들리지 않는다**는 데 있다.

### 정리: 하이브리드 추출의 실제 모습

| 단계 | 하는 일 | 왜 |
|---|---|---|
| 규칙 먼저 | 문장 틀이 있는 부분을 정규식으로 | 정확하고, 방향이 확실하고, 공짜 |
| 남은 것만 LLM | 규칙이 못 읽은 조각만 | 호출을 줄인다 |
| 노드 병합 | 같은 것이 두 번 만들어지면 합친다 | 이름 바꾸기로는 안 된다 |
| 충돌 해소 | 겹치는 사실은 규칙을 믿는다 | 안 하면 섞은 만큼 오류도 섞인다 |

마지막 두 줄이 이번 실험에서 배운 것이다. "섞는다"는 건 단순히 두 결과를 합치는 게 아니라
**같은 사실이 두 번 나올 때 무엇을 할지 정하는 일**이다.

## 🔗 코드와 연결

```bash
.venv/bin/python code/Q0017_hybrid_extraction.py
```

| 함수 | 역할 |
|---|---|
| `rule_extract()` | Q0011의 규칙 5개 |
| `run_hybrid()` | 규칙이 읽은 조각과 못 읽은 조각을 나눠 처리 |
| `merge_into()` | 중복 노드를 정식 노드로 병합 (`apoc.refactor.mergeNodes`) |
| `resolve_conflicts()` | 규칙 관계의 역방향 LLM 관계를 삭제 |

`resolve_conflicts()` 호출을 주석 처리하고 돌리면 방향 오류가 2개로 돌아온다.
