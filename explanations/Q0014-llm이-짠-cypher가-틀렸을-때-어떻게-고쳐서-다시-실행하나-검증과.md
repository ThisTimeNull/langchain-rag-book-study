# Q0014 · LLM이 짠 Cypher가 틀렸을 때 어떻게 고쳐서 다시 실행하나? (검증과 재시도)

- **태그**: graphrag
- **날짜**: 2026-09-12
- **코드**: [`code/Q0014_cypher_repair.py`](../code/Q0014_cypher_repair.py)

## ❓ 질문
Q0013에서 같은 질문에 17개, 19개, 20개가 번갈아 나왔다. 그래프는 정확한데 LLM이 매번
다른 Cypher를 쓴다. 검증하고 재시도하면 잡을 수 있을까?

## 💡 한 줄 답
> **검증(스키마, 문법, 0건)은 의미 오류를 하나도 못 잡았다.** 재시도는 한 번도 일어나지 않았다.
> 대신 **틀린 패턴을 예시로 보여주는 것(few-shot)이 효과가 있었다.** 0/5가 5/5로 바뀌었다.
> 단, 예시는 다른 질문에 부작용을 냈다.

## 📖 설명

### 실험 설계

같은 질문 3개를 5번씩 돌렸다. 한 번 맞힌다고 믿을 수 없으니 **얼마나 자주 맞히는지**를 본다.

| 질문 | 정답 |
|---|---|
| 감사 로그가 직접 또는 간접으로 의존하는 서비스는 몇 개? | 17개 |
| 결제 API 의존 서비스를 운영하는 팀의 온콜은? | 김철수 |
| 인프라팀이 운영하는 서비스에 의존하는 서비스는? | 결제 API, 이미지 CDN, 감사 로그 |

그래프는 Q0013과 같다. 규칙으로 적재해서 정확하고 매번 같다. 그러니 틀리면 전부 Cypher 탓이다.

세 방식을 비교했다.

1. **검증 없음**: Cypher를 한 번 만들고 그대로 실행
2. **검증 + 재시도**: 만든 쿼리를 세 가지로 검사하고, 걸리면 이유를 알려주고 다시 만들게 함
3. **예시 + 검증 + 재시도**: 2번에 "이런 패턴은 틀리다"는 예시를 프롬프트에 추가

검증 세 가지는 이것이다.

```python
check_schema()   쿼리에 쓴 라벨과 관계 이름이 실제 스키마에 있는가
check_syntax()   EXPLAIN 으로 문법이 맞는가
결과가 비었는가   0건이면 "시작점 id와 방향을 다시 보라"고 알려주고 재생성
```

### 결과

| 방식 | 질문 1 | 질문 2 | 질문 3 | 합계 |
|---|:---:|:---:|:---:|:---:|
| 검증 없음 | 2/5 | 5/5 | 5/5 | 13/15 (87%) |
| 검증 + 재시도 | **0/5** | 5/5 | 5/5 | 10/15 (67%) |
| 예시 + 검증 + 재시도 | **5/5** | 5/5 | 4/5 | 14/15 (93%) |

### ⭐ 발견 1: 검증은 의미 오류를 못 잡는다

검증 + 재시도 모드에서 **재시도가 한 번도 일어나지 않았다.** 그런데 질문 1은 5번 모두 틀렸다.
다섯 번 다 **18개**라고 답했다.

```cypher
MATCH (s:서비스 {id:'감사 로그'})-[:의존*0..]->(d:서비스) RETURN count(DISTINCT d)
```

`*0..`은 길이 0인 경로, 즉 시작점 자신을 포함한다. 그래서 17개에 감사 로그 하나가 더 붙어 18개다.
이 쿼리는 스키마에 있는 이름만 쓰고, 문법도 맞고, 결과도 나온다. **검증 세 개가 전부 통과한다.**

검증은 "틀린 쿼리"를 잡는 게 아니다. **"틀린 줄 알 수 있는 쿼리"를 잡는다.**
문법 오류, 없는 라벨, 0건은 기계가 안다. 하지만 "17이어야 할 것이 18이다"는 정답을 모르면
알 수가 없다. 그리고 정답을 알면 질문을 할 필요가 없다.

### ⭐ 발견 2: 예시가 의미 오류를 잡았다

프롬프트에 이 예시를 넣었다.

```
질문: X가 직접 또는 간접으로 의존하는 서비스는 몇 개인가요?
잘못된 쿼리: MATCH (s {id:'X'})-[:의존*0..]->(d) RETURN count(DISTINCT d)
  -> *0.. 은 시작점 자신을 포함하므로 하나가 더 세어진다.
올바른 쿼리: MATCH (s {id:'X'})-[:의존*1..]->(d) RETURN count(DISTINCT d)
```

질문 1이 **0/5에서 5/5로** 바뀌었다. 다섯 번 모두 17개.

LLM은 `*0..`과 `*1..`의 차이를 모르는 게 아니다. 어느 쪽을 써야 할지 **이 그래프의 맥락에서**
판단할 근거가 없었던 것이다. 예시가 그 근거를 준다.

### ⭐ 발견 3: 예시는 부작용을 낸다

같은 예시를 넣었더니 질문 3이 5/5에서 4/5로 **떨어졌다.** 답 내용도 달라졌다.

```
예시 없음: 감사 로그, 이미지 CDN, 결제 API              (직접 의존, 정답)
예시 있음: 감사 로그, 피처 스토어, A/B 테스트, 이미지 CDN, 쿠폰 엔진 ...  (간접까지 포함)
```

질문 3은 "의존하는"이라고만 했다. 직접 의존을 묻는 것이다. 그런데 예시에서 `*1..`을 배운
LLM이 여기에도 `*1..`을 써서 간접 의존까지 다 끌어왔다.
**예시 하나가 "의존이 나오면 무조건 사슬을 타라"는 편향을 만들었다.**

한 번은 0건이 나왔다. 검증이 "0건"을 잡아 3번 재시도했지만 끝내 못 고쳤다.
이것이 재시도가 실제로 일어난 유일한 사례다.

### ⭐ 발견 4: 검증 없음도 실행마다 흔들린다

같은 코드를 두 번 돌렸을 때 검증 없음 모드의 점수가 11/15에서 13/15로 달랐다.
LLM이 같은 입력에 다른 쿼리를 쓰기 때문이다.
**한 번 돌려서 맞았다고 "된다"고 말하면 안 된다.** 이 실험을 5회 반복으로 설계한 이유다.

### 그래서 무엇을 해야 하나

이번 실험에서 나온 순서대로 정리하면 이렇다.

| 수단 | 잡는 것 | 못 잡는 것 |
|---|---|---|
| 스키마, 문법, 0건 검증 | 기계가 알 수 있는 오류 | 실행되지만 틀린 쿼리 |
| 예시(few-shot) | 알려진 의미 오류 패턴 | 예시가 만든 편향, 새로운 패턴 |
| **질문 유형별 템플릿** | 자주 나오는 질문 전부 | 처음 보는 질문 |

마지막 줄이 실무에서 가장 많이 쓰는 방식이다. "X가 의존하는 서비스 개수"처럼 자주 묻는 질문은
**Cypher를 사람이 미리 써두고 X만 채운다.** LLM은 질문을 분류하고 X를 뽑는 일만 한다.
매번 새로 쿼리를 짓게 하지 않으니 흔들리지 않는다. 새로운 질문만 LLM에게 맡긴다.

> 정리하면, "LLM이 Cypher를 짠다"는 건 GraphRAG에서 **가장 믿을 수 없는 단계**다.
> 그래서 그 단계를 최소화하는 쪽으로 설계가 간다.

## 🔗 코드와 연결

```bash
.venv/bin/python code/Q0014_cypher_repair.py            # 질문당 5회
.venv/bin/python code/Q0014_cypher_repair.py --runs 10  # 더 많이 돌려 편차 확인
```

| 함수 | 역할 |
|---|---|
| `check_schema()` | 정규식으로 라벨과 관계 이름을 뽑아 실제 스키마와 대조 |
| `check_syntax()` | `EXPLAIN` 으로 문법 검사 (실행은 안 함) |
| `run_with_repair()` | 검증 실패 시 이유를 프롬프트에 붙여 최대 3번 재생성 |
| `FEW_SHOT` | 틀린 쿼리와 맞는 쿼리를 나란히 보여주는 예시 |

`FEW_SHOT`의 예시 문구를 바꿔 돌리면 질문 3의 답이 어떻게 달라지는지 볼 수 있다.
