# Q0010 · GraphRAG는 VectorRAG와 무엇이 다른가? (LLM으로 문서에서 그래프를 만들고 질의하기)

- **태그**: graphrag
- **날짜**: 2026-09-05
- **코드**: [`code/Q0010_graphrag_pipeline.py`](../code/Q0010_graphrag_pipeline.py)

## ❓ 질문
같은 문서로 GraphRAG를 만들면 VectorRAG와 무엇이 어떻게 달라지나?

## 💡 한 줄 답
> **LLM이 쓰이는 지점이 1곳에서 3곳으로 늘어난다.** 그 대가로 준비가 비싸지고
> **결과가 매번 달라진다.**
> 그리고 이번 실험의 결론: **문서가 평평한 규칙 나열이면 GraphRAG가 VectorRAG에 진다.**

## 📖 설명

### 파이프라인 비교

```
VectorRAG: 로드 → 청킹 → 임베딩 → FAISS → 거리검색 → 생성(LLM)
                          ↑ 결정적                      ↑ LLM 1곳

GraphRAG : 로드 → ①엔티티, 관계 추출(LLM) → Neo4j → ②질문→Cypher(LLM) → 실행 → 생성(LLM)
                  ↑ 비결정적, 비쌈                      ↑ LLM 3곳
```

### 실측, 같은 문서, 같은 질문

문서 3개(`data/sample/*.md`)로 양쪽을 만들고 세 질문을 던졌다.
LLM은 Azure AI Foundry의 `gpt-5.4-mini`, 임베딩은 `text-embedding-3-small`.

| 질문 | VectorRAG | GraphRAG |
|---|---|---|
| 연차는 며칠 전까지 신청? | ✅ "3일 전까지" | ❌ **"매 분기 말까지 인사팀에 제출"** (엉뚱한 답) |
| '개발 가이드'에 포함된 항목은? | ❌ 찾을 수 없음 | ❌ I don't know |
| 휴가에 포함되는 제도는? | ✅ "연차, 경조사 휴가" | ✅ "연차, 경조사 휴가, 이월, 소멸 규정" |

**GraphRAG가 1승 1무 1패로 졌다.** 특히 1번은 *틀린 답을 자신 있게* 내놨다,
LLM이 만든 Cypher가 엉뚱한 노드를 잡아왔고, 생성 단계는 그걸 그대로 믿었다.

### ⭐ 왜 졌나, 문서의 성격이 안 맞는다

우리 샘플 문서는 **평평한 규칙 나열**이다.

```markdown
## 휴가
- 연차는 입사 첫 해 11일, 2년 차부터 15일이 부여된다.
- 연차는 사용 3일 전까지 신청해야 하며, 팀장 승인 후 확정된다.
```

여기엔 **따라갈 관계가 없다.** 한 문단 안에 답이 통째로 들어 있으니
[[Q0007-rag-파이프라인을-처음부터-끝까지-직접-만들어보자-로드-청킹-임베딩-저]]의 벡터 검색이면 충분하다.
그래프로 만들면 오히려 문장이 조각나 **정보가 손실된다**, "3일 전까지 신청"이라는 사실이
`(연차)-[포함]->(팀장)` 같은 부실한 관계로 뭉개졌다.

> GraphRAG는 **관계 자체가 데이터일 때** 쓰는 것이다
> ([[Q0004-데이터베이스는-종류별로-언제-써야-하나-정형db-문서db-vectordb]]에서 그래프 DB를 언제 쓰냐고 했던 그 기준 그대로).
> 인물, 조직, 부품처럼 서로 얽힌 대상이 있고 "몇 다리 건너"를 물어야 GraphRAG가 산다.

### ⭐ 비결정성, 두 번 돌렸더니 그래프가 달라졌다

같은 문서, 같은 코드, 같은 모델로 **두 번 추출했더니 결과가 달랐다.**

| | 1차 실행 | 2차 실행(`--rebuild`) |
|---|---|---|
| 엔티티 수 | 24개 | **31개** |
| 라벨 | 문서, 제도, 규칙, 부서, 기간 | 문서, **규칙**, 부서, 기간 (`제도` 사라짐) |
| 문서 노드 | `한빛소프트 개발 가이드` 있음 | **없어짐** |

2번 질문이 1차엔 답할 수 있었는데 2차엔 못 하게 된 이유가 이것이다.
**임베딩은 같은 입력이면 항상 같은 벡터를 준다. LLM 추출은 그렇지 않다.**
이 차이가 운영에서 뼈아프다, 문서를 추가할 때마다 그래프가 조금씩 흔들린다.

### ⭐ 추출 오류, 실제로 뽑힌 것들

2차 실행에서 나온 관계 25개 중 명백히 틀린 것들:

```
(연차)      -[포함]->    (팀장)         ← 팀장은 연차에 '포함'되지 않는다
(자기계발비) -[포함]->    (인사팀)        ← 제출처지 하위 항목이 아니다
(코드 리뷰)  -[포함]->    (#Incident)   ← #incident는 장애 대응 채널이다
(사내 점심 식대) -[기한]-> (12,000원)     ← 금액을 '기한'으로 잡았다
```

관계 이름이 `포함`/`적용대상`/`기한` 세 개로 제한돼 있어서, **거기에 안 맞는 사실도
억지로 셋 중 하나에 밀어 넣은** 결과다. 제약을 풀면 라벨이 난립하고, 조이면 이렇게 왜곡된다.
**이 균형 잡기가 GraphRAG 실무의 대부분**이다.

### 코드에서 짚어둘 것

**`allowed_nodes` / `allowed_relationships`**
```python
LLMGraphTransformer(
    llm=llm,
    allowed_nodes=["문서", "제도", "규칙", "부서", "기간"],
    allowed_relationships=["포함", "적용대상", "기한"],
)
```
안 주면 LLM이 `규정`/`정책`/`규칙`처럼 같은 뜻의 라벨을 제각각 만들어낸다. 주면 위처럼 왜곡된다.

**공통 라벨을 붙이지 말 것 (실패에서 배운 것)**
처음엔 정리하기 쉬우라고 모든 노드에 `:Q0010` 라벨을 붙였는데, 그게 **스키마에 노출되면서
LLM이 Cypher를 짤 때 어느 라벨로 매칭할지 헷갈려** 정확도가 떨어졌다.
LLM에게 보여줄 스키마는 깨끗해야 한다.

**`allow_dangerous_requests=True`**
```python
GraphCypherQAChain.from_llm(llm, graph=graph, allow_dangerous_requests=True)
```
**LLM이 만든 쿼리를 그대로 DB에 실행**하기 때문에 명시적 동의를 요구한다.
LLM이 `DETACH DELETE`를 생성하면 그대로 지워진다, 운영이라면 **읽기 전용 계정**으로 붙여야 한다.

## 🔗 코드와 연결

```bash
.venv/bin/python code/Q0010_graphrag_pipeline.py            # 기존 그래프 재사용
.venv/bin/python code/Q0010_graphrag_pipeline.py --rebuild  # LLM으로 다시 추출
```

| 파트 | 내용 |
|---|---|
| 1 | `LLMGraphTransformer`로 문서 → 엔티티, 관계 추출 후 Neo4j 적재 |
| 2 | 만들어진 그래프의 라벨, 관계, 샘플 확인 |
| 3 | `GraphCypherQAChain`, LLM에 넘어가는 스키마 확인 |
| 4 | 같은 질문 3개를 VectorRAG, GraphRAG에 각각 던져 비교 |

`--rebuild`를 두 번 돌려보면 비결정성을 직접 볼 수 있다.
