# Q0004 · 데이터베이스는 종류별로 언제 써야 하나? (정형DB, 문서DB, VectorDB, GraphDB 선택 기준)

- **태그**: concept
- **날짜**: 2026-08-18
- **코드**: [`code/Q0004_db_selection.py`](../code/Q0004_db_selection.py)

## ❓ 질문
GraphDB, JsonDB, VectorDB, 정형DB, DocumentDB… 종류가 너무 많은데 각각 언제 써야 하나?

## 💡 한 줄 답
> **데이터의 모양이 아니라 "내가 던질 질문의 모양"으로 고른다.**
> 세고 합치면 정형DB, 필드가 제각각이면 문서DB, 관계를 따라가면 그래프DB, 뜻으로 찾으면 벡터DB.

## 📖 설명

### 한눈에 보는 표

| 종류 | 저장 단위 | **이런 질문에 강하다** | 대표 제품 |
|---|---|---|---|
| **정형 DB** (RDB) | 행 × 열 (테이블) | "개발팀 평균 연차는?", 세기, 합치기, 정확한 조건 | PostgreSQL, MySQL |
| **문서 DB** (Document) | JSON 문서 1개 | "이 사원의 모든 정보를 통째로 줘", 필드가 제각각 | MongoDB, Firestore |
| **키-값 DB** | 키 → 값 | "이 세션 토큰 유효해?", 초고속 단순 조회, 캐시 | Redis, DynamoDB |
| **그래프 DB** | 노드 + 관계(간선) | "A와 B는 몇 다리 건너 연결돼 있나?" | **Neo4j** |
| **벡터 DB** | 문장 → 숫자 배열 | "클라우드 잘 아는 사람?", 단어가 안 겹쳐도 뜻으로 검색 | FAISS, Chroma, Pinecone |

> 📌 **"JsonDB"는 별도 종류가 아니다.** 보통 *문서 DB*(MongoDB처럼 JSON을 통째로 저장)를 가리키거나,
> 작은 JSON 파일 하나를 DB처럼 쓰는 걸 말한다. 참고로 요즘은 PostgreSQL도 `JSONB` 컬럼으로
> JSON을 잘 다뤄서, **"JSON 쓰려고 굳이 문서 DB로 갈아탈" 이유는 예전보다 줄었다.**

### 고르는 순서 (실무에서 실제로 밟는 길)

```
1. 일단 정형 DB(PostgreSQL)로 시작한다   ← 90%는 여기서 끝난다
        │
        ├─ 레코드마다 필드가 너무 달라 컬럼이 NULL 투성이?  → 문서 DB
        ├─ 그냥 빠른 조회/캐시만 필요?                     → 키-값 DB
        ├─ "몇 다리 건너"를 계속 물어보게 되나?             → 그래프 DB
        └─ 단어가 아니라 '의미'로 찾아야 하나? (LLM/RAG)    → 벡터 DB
```

**핵심은 "무엇을 저장하나"가 아니라 "무엇을 물어보나"다.** 사원 정보는 5가지 DB 어디에나
넣을 수 있다. 갈리는 건 질문이다, 코드에서 같은 데이터로 4번 실험한 게 정확히 이 지점이다.

### 종류별로 조금 더

**정형 DB**, 표로 정리되고 관계가 안정적이면 기본값이다. 집계(`COUNT`/`AVG`)와
**트랜잭션**(돈 계산처럼 "중간에 깨지면 안 되는 작업")은 여기가 압도적이다.
단점: 스키마를 바꾸려면 마이그레이션이 필요하고, 의미 검색은 아예 못 한다.

**문서 DB**, 스키마를 안 정해도 넣을 수 있다. 사원마다 자격증, 포트폴리오, 외국어처럼
가진 필드가 다를 때 표로 만들면 빈칸 지옥이 되는데, 문서 DB는 그냥 넣는다.
단점: 여러 컬렉션을 넘나드는 JOIN, 복잡한 집계는 정형 DB가 낫다.

**그래프 DB**, "친구의 친구", "이 부품이 들어간 완제품의 납품처" 같은 **경로 질문**이 핵심.
SQL로도 못 하는 건 아니지만 *몇 다리인지 모르면* 셀프 JOIN을 몇 번 걸어야 할지 미리 정할 수 없다.
그래프 DB는 이걸 한 줄로 쓴다 (Cypher: `MATCH (a)-[*]-(b)`). **관계 자체가 데이터일 때** 쓴다.

**벡터 DB**, 문장을 숫자 배열(임베딩)로 바꿔 저장하고, "가까운 벡터"를 찾는다.
질문에 없던 단어라도 뜻이 통하면 찾아낸다 → 이게 [[Q0001-rag는-왜-필요한가]]의 검색 단계다.
단점: **정확한 답을 보장하지 않는다.** "가장 비슷한 것"을 줄 뿐이라 집계, 조건 필터에는 못 쓴다.

### 이 프로젝트와의 관계, VectorRAG vs GraphRAG

지금 보는 책의 두 축이 정확히 이 선택 문제다.

| | **VectorRAG** (벡터 DB) | **GraphRAG** (그래프 DB) |
|---|---|---|
| 잘 맞는 질문 | "환불 규정이 뭐야?" (문서 한 조각에 답이 있음) | "이 규정이 바뀌면 영향받는 팀은?" (여러 사실을 이어야 함) |
| 방식 | 비슷한 문서 조각을 찾아 LLM에 넘김 | 관계를 따라가며 사실을 모아 LLM에 넘김 |
| 한계 | 흩어진 정보를 종합, 요약하는 질문에 약함 | 그래프를 만드는 비용이 크다 |

실무에선 **둘 다 쓴다.** Neo4j처럼 그래프 DB에 벡터 인덱스가 같이 들어있는 제품도 있고,
"벡터로 후보를 찾고 → 그래프로 주변 사실을 확장"하는 하이브리드가 흔하다.

> ⚠️ 흔한 오해: "RAG니까 벡터 DB만 있으면 된다" → 아니다. 실제 서비스는
> 사용자, 주문 정보는 정형 DB, 문서 검색은 벡터 DB로 **역할을 나눠 쓴다** (polyglot persistence).

## 🔗 코드와 연결

[`code/Q0004_db_selection.py`](../code/Q0004_db_selection.py)는 **똑같은 사원 6명 데이터**를
4가지 DB에 넣고, 각각이 잘하는 질문을 실제로 실행해 보여준다.

| 파트 | 질문 | 결과 |
|---|---|---|
| 1) SQLite | "부서별 인원수, 평균 연차는?" | 개발팀 3명 3.7년 … (집계는 SQL이 한 줄) |
| 2) JSON | 사원마다 다른 필드 저장 | 표로 만들면 NULL 투성이가 될 데이터를 그대로 저장 |
| 3) networkx | "김철수 ↔ 최지민 협업 경로는?" | 김철수 → 박영희 → 이민수 → 최지민 (3다리) |
| 4) FAISS | "클라우드 인프라 잘 다루는 사람?" | LIKE 검색 **0건** vs 벡터 검색이 김철수, 최지민 찾아냄 |

가장 중요한 건 **4번의 대비**다. 사원 소개글에 "클라우드"라는 단어를 쓴 사람이 아무도 없어서
`LIKE '%클라우드%'`는 0건이지만, 벡터 검색은 "서버 배포, 컨테이너", "쿠버네티스"를
같은 의미로 잡아낸다. 이게 키워드 검색과 벡터 검색의 결정적 차이다.

> 💡 코드에는 학습 포인트가 하나 더 숨어 있다: 임베딩 모델을 영어 전용
> `all-MiniLM-L6-v2`로 바꾸면 **한국어 의미를 못 잡아 엉뚱한 사람이 뽑힌다.**
> 벡터 DB의 성능은 DB가 아니라 **임베딩 모델**이 좌우한다.
