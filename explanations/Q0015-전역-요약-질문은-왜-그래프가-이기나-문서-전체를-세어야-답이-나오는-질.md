# Q0015 · 전역 요약 질문은 왜 그래프가 이기나? (문서 전체를 세어야 답이 나오는 질문)

- **태그**: graphrag
- **날짜**: 2026-09-13
- **코드**: [`code/Q0015_global_summary.py`](../code/Q0015_global_summary.py)

## ❓ 질문
지금까지 그래프가 확실히 이긴 건 "긴 사슬" 하나였다. 그래프가 이기는 유형이 또 있나?

## 💡 한 줄 답
> 있다. **문서 전체를 세어야 답이 나오는 질문**이다.
> 벡터는 k개만 보니 구조적으로 못 풀고, **전체를 다 넣어줘도 LLM이 잘못 셌다.**
> 그래프는 집계 한 줄로 맞혔다. 단, 세는 단위를 통일하는 추출이 먼저다.

## 📖 설명

### 실험 설계

장애 회고 24건을 만들었다. 원인 분포를 미리 정해두고 그게 정답이다.

```
배포 실수 8건, 커넥션 고갈 6건, 디스크 부족 4건, 외부 API 지연 3건, 설정 오류 3건
```

회고마다 서술은 다르게 썼다. "롤백 대상 설정이 함께 배포됐다", "마이그레이션 순서가 꼬였다",
"배포 스크립트가 옛 이미지를 가리켰다"는 전부 배포 실수다. 마지막 줄에만
"원인은 배포 실수로 분류했다"라고 적었다. 실제 회고에 분류 필드가 있는 것과 같다.

질문은 세 개다.

| 질문 | 유형 | 정답 |
|---|---|---|
| 가장 자주 나온 원인은 무엇이고 몇 건? | 전역 | 배포 실수, 8건 |
| 커넥션 고갈로 분류된 장애는 몇 건? | 전역 | 6건 |
| 회고 03에서 영향받은 서비스는? | 국소 | 인증 서비스 |

### 결과

| | 벡터 k=4 | 벡터 k=24 (전체) | 그래프 |
|---|:---:|:---:|:---:|
| 가장 잦은 원인 (8건) | ❌ 찾을 수 없음 | ❌ **7건** | ✅ 8건 |
| 커넥션 고갈 (6건) | ❌ 4건 | ❌ 찾을 수 없음 | ✅ 6건 |
| 회고 03 (국소) | ✅ | ✅ | ✅ |

### ⭐ 발견 1: 벡터는 전역 질문에 구조적으로 답할 수 없다

k=4는 24건 중 4건만 본다. 나머지 20건은 존재하지 않는 것과 같다.
"커넥션 고갈이 몇 건?"에 4건이라고 답한 건, **자기가 본 4건 안에서** 센 것이다.
틀렸다는 걸 스스로 알 방법이 없다.

이건 튜닝으로 고칠 수 없다. k를 올리는 것 말고는 방법이 없고, 그건 다음 문제로 이어진다.

### ⭐ 발견 2: 전체를 다 넣어줘도 틀린다

k=24로 24건을 전부 넣었다. 근거가 2,972자다. 그런데도 틀렸다.

- 배포 실수를 **7건**이라고 셌다. 정답은 8건이다
- 커넥션 고갈은 **"찾을 수 없다"**고 했다. 근거 안에 6건이 분명히 있는데도

LLM은 긴 문맥에서 세는 일을 잘 못한다. Q0013에서 근거 126개를 주니 헷갈렸던 것과 같은 현상이다.
그리고 24건이니까 넣을 수 있었다. **회고가 2,400건이면 넣을 수도 없다.**

### ⭐ 발견 3: 그래프는 집계 한 줄이다

```cypher
MATCH (i:장애)-[:원인]->(c:원인)
RETURN c.id, count(DISTINCT i) AS n ORDER BY n DESC
```

건수가 24건이든 2만 건이든 같은 쿼리다. DB가 세니 틀리지 않는다.
**이게 Microsoft가 GraphRAG를 만든 이유다.** "이 문서 더미의 주요 주제는?" 같은 질문은
top-k로는 답할 수 없고, 구조를 만들어 놓고 집계해야 한다.

### ⭐ 발견 4: 세는 단위가 통일돼야 한다 (이게 제일 어려웠다)

처음에는 Q0010부터 써온 자유 추출(`LLMGraphTransformer`)로 그래프를 만들었다.
결과는 이랬다.

```
원인 노드 23개:
  배포 실수, 롤백 대상 설정, 롤백 대상 설정 배포, 마이그레이션 순서가 꼬인 것,
  배포 스크립트, 새 버전 배포, 옛 이미지, 커넥션 고갈, 커넥션 대기 지연,
  커넥션이 반환되지 않는 경로, Db 커넥션 풀이 바닥났다, 트래픽 증가, ...
```

정답 분류는 5개인데 **23개로 흩어졌다.** 서술을 그대로 노드로 만든 것이다.
이 그래프로 집계하면 "가장 잦은 원인은 공간 부족, 2건"이라는 엉뚱한 답이 나왔다.

그래서 추출 방식을 바꿨다. LLM에게 **다섯 가지 중 하나를 고르라고 강제**했다.

```python
class Incident(BaseModel):
    incident_id: str
    cause: Literal["배포 실수", "커넥션 고갈", "디스크 부족", "외부 API 지연", "설정 오류"]
    service: str
    team: str

extractor = llm.with_structured_output(Incident)
```

이렇게 하니 24건 모두 정답 분포와 **정확히 일치**했다.

| 원인 | 정답 | 그래프 |
|---|:---:|:---:|
| 배포 실수 | 8 | 8 |
| 커넥션 고갈 | 6 | 6 |
| 디스크 부족 | 4 | 4 |
| 외부 API 지연 | 3 | 3 |
| 설정 오류 | 3 | 3 |

**둘 다 LLM 추출이다.** 차이는 그래프 모양을 누가 정하느냐다. 자유 추출은 LLM이 정한다.
고정 스키마는 사람이 정하고 LLM은 빈칸만 채운다. 전역 집계를 하려면 후자여야 한다.

> Q0011의 교훈이 여기서 다시 나온다. "이 데이터, 정말 LLM이 읽어야 하나?"에 이어
> "LLM이 읽더라도, 그래프 모양까지 LLM에게 맡겨야 하나?"를 물어야 한다.
> 세야 하는 것이 있으면 그 단위는 사람이 정해야 한다.

### 그래프가 이기는 질문 유형, 정리

세 실험(Q0011, Q0013, Q0015)을 거쳐 확인한 것이다.

| 유형 | 예 | 벡터가 못 하는 이유 |
|---|---|---|
| 긴 사슬 | X가 간접 의존하는 서비스 전부 | 사슬 링크를 조각 k개로 못 모은다 |
| **전역 집계** | 가장 잦은 원인은? 총 몇 건? | k개만 본다. 전체를 넣어도 잘못 센다 |
| 구조 조건 | 인프라팀이 운영하는 서비스에 의존하는 것 | 조인이 필요하다 |

그 밖의 질문, 즉 "답이 어딘가에 적혀 있는" 질문은 벡터로 충분하다. 그리고 그게 대부분이다.

## 🔗 코드와 연결

```bash
.venv/bin/python code/Q0015_global_summary.py --rebuild
```

| 함수 | 역할 |
|---|---|
| `build_graph_free()` | 자유 추출. 원인 노드가 몇 개로 흩어지는지 보여주고 지운다 |
| `build_graph_typed()` | 고정 스키마 추출. `with_structured_output` + `Literal` 로 택일 강제 |
| `check_extraction()` | 정답 분포와 대조 |
| `vector_runner(k)` | k=4와 k=전체를 같은 함수로 |

`data/incident_sample/`은 생성 스크립트로 만들었다. 원인 분포를 바꿔 다시 만들면
정답도 같이 바뀐다.
