# Q0013 · 하이브리드 검색은 어떻게 하나? (벡터로 진입점을 찾고 그래프로 확장하기)

- **태그**: graphrag
- **날짜**: 2026-09-09
- **코드**: [`code/Q0013_hybrid_search.py`](../code/Q0013_hybrid_search.py)

## ❓ 질문
벡터와 그래프를 같이 쓰면 서로의 약점을 메울 수 있을까?

## 💡 한 줄 답
> 메울 수 있다. 단 **"근거를 합치는" 방식이 아니라 "질문을 나누는" 방식**이어야 했다.
> 근거를 많이 모아 LLM에 넘길수록 답이 오히려 나빠졌다.

## 📖 설명

### 실험 설계

코퍼스를 일부러 두 종류로 섞었다.

```
data/hybrid_sample/
  team_roster.md, service_owner.md, service_deps.md, oncall.md   구조화된 문서
  notes.md                                                       서술형 메모
```

`notes.md`에는 "인증 서비스의 세션 만료 시간은 30분" 같은 내용이 문장으로만 있다.
문장 틀이 없어서 규칙이 못 읽고, 따라서 **그래프에 안 들어간다.**
반대로 의존 사슬은 구조화 문서에 있어서 그래프에 정확히 들어간다.

이제 각 저장소가 하나씩 못 푸는 질문이 생긴다.

### 결과

| 질문 | 벡터만 | 그래프만 | 합치기 | 라우팅 |
|---|:---:|:---:|:---:|:---:|
| 인증 서비스 세션 만료 시간은? (정답 30분) | ✅ | ❌ | ✅ | ✅ |
| 감사 로그가 의존하는 서비스 개수는? (정답 17개) | ❌ 2개 | ✅ 17개 | ❌ 15개 | ❌ 19개 |
| 결제 API 의존 서비스 운영팀의 온콜은? (정답 김철수) | ❌ | ✅ | ❌ | ✅ |

### ⭐ 발견 1: 근거를 합치면 오히려 나빠진다

처음 만든 하이브리드는 교과서에 나오는 그 방식이었다.

```
질문 -> 벡터 검색 -> 나온 텍스트에서 엔티티 찾기 -> 그래프로 이웃 확장
     -> 텍스트 근거 + 그래프 근거를 함께 LLM에 전달
```

확장 범위를 세 번 바꿔가며 돌렸다.

| 설정 | LLM에 준 그래프 사실 | 3다리 질문 |
|---|---:|:---:|
| 진입점 제한 없음, 1홉 | 145개 | ❌ |
| 진입점 4개, 1홉 | 28개 | ❌ |
| 진입점 4개, 2홉 | 69개 | 부분 정답 |

**정보를 더 줄수록 좋아지지 않았다.** 사실 126개를 준 질문에서는 아예
"문서에서 찾을 수 없습니다"라고 답했다. 근거 더미에 답이 묻힌 것이다.

이유는 분명하다. 이 방식은 **LLM에게 조인을 시키는 것**이다.
`결제 API -의존-> 인증 서비스`, `인프라팀 -운영-> 인증 서비스`, `김철수 -온콜-> 인프라팀`
세 줄을 던져주고 "알아서 이어봐"라고 하는 셈이다. DB가 한 줄로 하는 일을
LLM에게 자연어로 시키니 잘 될 리가 없다.

### ⭐ 발견 2: 나누면 된다 (라우팅)

그래서 방향을 바꿨다. 합치지 않고 **질문을 보고 한쪽으로 보낸다.**

```python
ROUTE_PROMPT = ...
  graph:  관계를 따라가거나, 개수를 세거나, 경로를 묻는 질문
  vector: 설명, 정책, 수치, 배경처럼 문장으로 서술된 내용을 묻는 질문
```

라우팅은 세 질문 모두 올바른 목적지를 골랐다.

```
세션 만료 시간   -> vector  ✅ 30분
의존 개수        -> graph   (목적지는 맞음)
3다리 온콜       -> graph   ✅ 김철수
```

**핵심은 계산 주체가 바뀌는 것이다.** 라우팅에서는 Cypher가 DB 안에서 경로를 세고,
LLM은 그 결과 숫자를 읽기만 한다. 합치기에서는 LLM이 triple 목록을 보고 직접 세야 했다.
그래서 15개, 19개처럼 답이 흔들렸다.

### ⭐ 발견 3: 라우팅도 만능은 아니다

2번 질문에서 라우팅은 목적지를 맞게 골랐는데 답이 19개로 틀렸다.
같은 실행에서 그래프만 쓴 경우는 17개로 맞았다.

차이는 **LLM이 매번 다른 Cypher를 쓴다**는 데 있다.

```cypher
-- 맞는 쿼리
MATCH (l:서비스 {id:'감사 로그'})-[:의존*1..]->(s:서비스) RETURN count(DISTINCT s)

-- 시작점을 잘못 잡은 쿼리 (문서에 언급된 모든 서비스에서 출발)
MATCH (d:Document)-[:MENTIONS]->(:서비스)-[:의존*0..]->(s:서비스) ... RETURN count(DISTINCT s)
```

라우팅이 옳은 저장소로 보내도, 그 저장소에서 쓸 쿼리가 틀리면 소용없다.
**이건 라우팅 문제가 아니라 Cypher 생성 문제다.** 다음 질문에서 다룬다.

### 실무에서 쓰는 하이브리드의 모습

이번 실험으로 정리하면 이렇다.

1. **라우팅을 기본으로 둔다.** 질문 유형을 먼저 판별한다
2. **집계와 경로는 DB에 맡긴다.** LLM에게 세게 하지 않는다
3. **근거 합치기는 보조로 쓴다.** 두 저장소 모두 필요한 질문에만, 그리고 범위를 좁혀서
4. **진입점을 좁히는 게 손잡이다.** 질문에 등장한 이름을 1순위로, 개수를 제한한다

## 🔗 코드와 연결

```bash
.venv/bin/python code/Q0013_hybrid_search.py
```

네 가지 방식을 같은 질문에 대해 나란히 실행한다.

| 함수 | 역할 |
|---|---|
| `build_graph()` | 규칙으로 그래프 적재 (Q0011에서 배운 방식) |
| `link_entities()` | 검색 결과에서 진입점 찾기. 질문에 나온 이름을 1순위로, 최대 4개 |
| `expand()` | 진입점 주변 2홉 경로와 의존 사슬 전체를 가져오기 |
| `route()` | 질문 유형을 판별해 목적지 결정 |

`link_entities()`의 `limit`을 바꿔가며 돌리면, 근거가 많아질수록 답이 나빠지는 걸
직접 볼 수 있다.
