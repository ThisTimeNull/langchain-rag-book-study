# Q0012 · LLM 추출이 이득인 경우는 언제인가? (비정형 문서에서 그래프 만들기)

- **태그**: graphrag
- **날짜**: 2026-09-06
- **코드**: [`code/Q0012_prose_extraction.py`](../code/Q0012_prose_extraction.py)

## ❓ 질문
[[Q0011-graphrag가-이기는-데이터는-어떤-모양인가-관계가-얽힌-문서로-다시]]에서 규칙 적재가 LLM 추출을 이겼다.
그럼 LLM 추출은 언제 쓰나? 회의록이나 뉴스처럼 틀이 없는 글에서는 반대가 될까?

## 💡 한 줄 답
> 정확히 반대가 된다. 같은 규칙, 같은 정답 기준으로,
> **정형 문서에서는 규칙 100% 대 LLM 67%,**
> **비정형 문서에서는 규칙 0% 대 LLM 82%였다.**

## 📖 설명

### 실험 설계

Q0011과 조건을 하나만 바꿨다. 문서를 사람이 자유롭게 쓴 글로 교체했다.

```
data/prose_sample/
  weekly_meeting.md    주간 회의 기록
  incident_review.md   장애 회고
  handover.md          인수인계 메모
```

같은 사실이 문서마다 다른 말로 적혀 있다.

```
"결제 API가 인증 서비스를 매번 두드리는데"      (회의록)
"인증을 기다리던 결제 API가 줄줄이 밀렸다"      (회고)
"로그인 확인 때문에 인증 서비스에 얹혀 있고"     (인수인계)
```

셋 다 "결제 API는 인증 서비스에 의존한다"는 한 가지 사실이다.

사람이 문서를 읽고 정답 11개를 손으로 정리했다. 이걸 기준으로 채점한다.

### 결과 1: 규칙은 0개를 잡았다

Q0011에서 100% 정확했던 정규식 규칙을 그대로 돌렸다.

```
팀장 규칙 -> 0개    소속 규칙 -> 0개    운영 규칙 -> 0개
의존 규칙 -> 0개    온콜 규칙 -> 0개
```

**하나도 못 잡는다.** `- (.+?)는 (.+?)에 의존한다\.` 같은 패턴은 "의존한다"라는 말이
문장에 실제로 있어야 걸린다. 사람은 그렇게 쓰지 않는다. "두드린다", "얹혀 있다",
"물고 있다", "바라본다"라고 쓴다. 이 표현을 미리 다 적어둘 방법이 없다.

### 결과 2: LLM은 11개 중 9개를 잡았다 (82%)

```
맞힌 것 9개
  (결제 API) -[의존]-> (인증 서비스)
  (인증 서비스) -[의존]-> (사용자 DB)
  (추천 엔진) -[의존]-> (결제 API)
  (알림 서비스) -[의존]-> (결제 API)
  (정하늘) -[팀장]-> (인프라팀)
  (이민수) -[팀장]-> (결제팀)
  (김철수) -[소속]-> (인프라팀)
  (한서준) -[소속]-> (인프라팀)
  (박영희) -[소속]-> (결제팀)

놓친 것 2개
  (인프라팀) -[운영]-> (인증 서비스)
  (인프라팀) -[운영]-> (알림 서비스)
```

문장이 제각각인데도 같은 사실로 묶어냈다. **이게 LLM 추출을 쓰는 이유다.**

놓친 2개는 이유가 있다. 원문이 "인증 서비스는 우리 팀 소관이라"처럼 썼다.
"우리 팀"이 인프라팀이라는 건 회의록 제목을 봐야 안다. 조각 단위로 자르면 그 맥락이 잘린다.

### 결과 3: 대신 쓰레기도 같이 나온다

정답에 없는데 뽑힌 것이 14개였다. 그중에는 이런 것들이 있다.

```
(그쪽) -[의존]-> (우리 쪽)        ← 대명사를 실체로 잡았다
(김철수) -[운영]-> (인증 서비스)   ← 김철수는 담당자지 운영 주체가 아니다
(알림 서비스) -[소속]-> (그쪽)     ← 관계 방향과 종류가 둘 다 틀렸다
```

**대명사 문제**가 눈에 띈다. "그쪽", "우리 쪽" 같은 말을 노드로 만들어 버린다.
사람은 앞뒤를 보고 누구인지 알지만, 조각 단위로 읽는 LLM은 모른다.
이걸 푸는 게 **상호참조 해결(coreference resolution)** 이고, 실무 GraphRAG 전처리의 큰 축이다.

전부 오류는 아니다. `(데이터팀) -[운영]-> (추천 엔진)`처럼 문서에 실제로 있는데
내 정답 목록에 안 넣은 것도 섞여 있다. 정답을 손으로 만들면 이런 누락이 생긴다.

### 결과 4: 그래도 질의는 벡터가 이겼다

추출을 82% 해냈다고 질의까지 이기는 건 아니다.

| 질문 | Vector | Graph |
|---|:---:|:---:|
| 결제 API가 의존하는 서비스는? | ✅ | ✅ |
| 인증 서비스를 운영하는 팀은? | ✅ | ❌ 모름 |
| 결제 API가 멈추면 영향받는 서비스는? | ✅ | ❌ 반대 방향을 탐색 |

2번은 놓친 `운영` 관계 때문에 실패했다. 3번은 화살표를 거꾸로 따라가야 하는데
LLM이 정방향으로 짰다. 그리고 코퍼스가 조각 6개뿐이라 벡터가 절반을 한 번에 본다.
[[Q0011-graphrag가-이기는-데이터는-어떤-모양인가-관계가-얽힌-문서로-다시]]에서 확인한 대로,
코퍼스가 작으면 벡터가 유리하다.

### 그래서 언제 무엇을 쓰나

| 데이터 모양 | 추출 방법 | 근거 |
|---|---|---|
| 문장 틀이 고정 (표, 로그, 정형 문서) | **규칙 또는 파서** | Q0011에서 규칙 100%, LLM 67% |
| 사람이 자유롭게 쓴 글 (회의록, 뉴스, 계약서) | **LLM** | Q0012에서 규칙 0%, LLM 82% |
| 둘이 섞여 있음 | 규칙으로 먼저 긁고, 남은 것만 LLM에 | 비용과 정확도를 같이 챙긴다 |

**추출 방법을 고르는 것과 질의 방법을 고르는 것은 별개다.** 이 실험에서 LLM 추출은
분명히 이득이었다. 규칙으로는 0개니까 애초에 그래프를 만들 수조차 없었다.
하지만 그렇게 만든 그래프로 질의해서 벡터를 이기려면 조건이 더 필요하다.
긴 사슬 질문, 충분히 큰 코퍼스, 그리고 정확한 그래프다.
